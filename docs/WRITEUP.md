# Write-up: driver qualifying lookup

A console app that reads the 2026 Australian GP qualifying lap times. Given a driver code, it shows
their best valid lap in Q1, Q2 and Q3, their final position, and how they compared with their
teammate.

## Build, run and test

It needs Python 3.10 or newer and has no third-party dependencies, so there's nothing to install.

```bash
uv run quali HUL       # report for one driver
uv run quali           # keeps asking for driver codes until you enter q
uv run quali --list    # list the driver codes
```

Without uv, from the repo root:

```bash
PYTHONPATH=src python -m qualifying HUL                # macOS / Linux
$env:PYTHONPATH = "src"; python -m qualifying HUL      # Windows PowerShell
```

Tests: `uv run pytest`, or `pip install pytest` then `python -m pytest`.

To re-run the analysis notebook, which needs pandas and Python 3.12+:
`uv run --group eda jupyter nbconvert --to notebook --execute --inplace notebooks/eda_session_laptimes.ipynb`

Example:

```
BOR · Audi
Classified P10 of 19
Reached Q3 but set no time; placed behind Q3 runners

Segment  Best lap   Rank  Gap
Q1       1:20.495   10    +0.988
Q2       1:20.221   10    +1.287
Q3       —          10            no time set

Insights
- Teammate HUL (P11): Q1 -0.529, Q2 -0.082 (faster in 2 of 2)
```

## Approach

I started by exploring the data (`notebooks/`, `docs/eda_findings.md`), because the file has a
few traps:
- out-laps have lap times, so Verstappen's "best" would be a 1:42 out-lap
- the reason given for a deleted lap names the wrong lap
- Bortoleto made the Q3 cut but has no Q3 laps in the file

I then wrote the rules down in `specs/driver-lookup.md`, with examples taken from the real data.
Next I wrote tests from the spec, and finally the code to make them pass.

## Architecture

```
┌────────────────────────────────────────────────────────────┐
│ cli.py                                                     │
│ arguments · interactive prompt · text output · exit codes  │
└────────────────────────────────────────────────────────────┘
             │                               │
             ▼                               ▼
┌──────────────────────────┐  ┌──────────────────────────────┐
│ load.py                  │  │ classification.py            │
│ raw JSON → Lap           │  │ insights.py · format.py      │
│ the only code that knows │  │ pure rules: no I/O and       │
│ the file format          │  │ no knowledge of the file     │
└──────────────────────────┘  └──────────────────────────────┘
             │                               │
             ▼                               ▼
┌────────────────────────────────────────────────────────────┐
│ models.py                                                  │
│ Lap · SegmentResult · DriverResult · SEGMENTS              │
└────────────────────────────────────────────────────────────┘
```

Arrows point to what a module imports.

- `models.py`: plain data classes.
- `load.py`: turns the JSON into `Lap` objects. It deals with the file's quirks: one list per
  field, `"None"` strings, booleans written as text, and bad values.
- `classification.py`: valid laps, best laps, who reached each segment, and the final order.
- `insights.py`: the teammate comparison.
- `format.py`: lap times as `m:ss.sss`.
- `cli.py`: arguments, the prompt and the output. It's the only module that reads input or prints.

A few choices worth explaining:
- **Standard library only.** It runs anywhere with Python 3.10+. I used pandas for the analysis
  but kept it in a separate dependency group.
- **One sort function** decides both who advances from each segment and the final order, so the
  rules live in one place.
- **Whole milliseconds.** Times are compared and formatted in whole milliseconds, to avoid float
  rounding errors in the last digit.
- **Models separate from the loader,** so the rules don't depend on the file format. A test
  checks the import direction.
- **One less module.** The valid-lap rule started in its own `laps.py`. I merged it into
  `classification.py` because it was one function with one caller.
- **Insights kept separate.** `insights.py` is also small, so why not merge it too? Because it
  isn't part of working out the result. Valid laps feed into the classification. Insights only
  read the finished classification and add commentary on top, so they can change without any
  risk to the positions, and the classification can be tested on its own. It's also where the
  spec's five later insights would go, so the module will grow.

## Assumptions and trade-offs

- **Valid lap:** it has a time and isn't deleted, an out-lap, an in-lap, interrupted by a red
  flag, or generated by the FastF1 library. Deletions come only from the `del` field.
- **Cut-offs are fixed:** the top 16 reach Q2 and the top 10 reach Q3 (2026 rules, 22 cars).
  Working them out from the data would have made Bortoleto a Q2 finisher, which isn't what
  happened. The downside is that a different grid size needs the constant changed.
- **No time in a segment the driver reached:** they're placed behind everyone who set a time
  there, so Bortoleto is P10. If several drivers are in that position, their previous segment's
  times decide the order.
- **No valid lap at all:** the driver isn't classified (Verstappen). The file has no earlier
  session to fall back on, and I deliberately used no other data sources.
- **Missing drivers:** Stroll and Sainz aren't in the file. Positions therefore run P1–P19 and
  won't match the official result below them.
- **Bad data:** bad values are treated as missing or the lap is skipped, with one warning
  giving the count. A file that can't be used at all gives an error and exit code 1.
- **Weather is ignored:** the per-lap weather in the file is attached to the wrong laps.

## Extra insight: teammate comparison

```
- Teammate HAM (P7): Q1 +0.415, Q2 -0.564, Q3 -0.151 (faster in 2 of 3)
```

Teammates drive the same car, so the gap between them says the most about the driver rather than
the car. The line shows:
- the gap in each segment where both set a time (negative means the selected driver was faster)
- how many of those segments the driver won
- the teammate's final position

It also covers a teammate with no time to compare and a teammate missing from the file.

I also considered the gap to pole, the margin to the elimination cut-off, a theoretical best from
best sectors, and red-flag impact. I picked the teammate comparison because it tells you the most
about the driver. The others are written up in the spec as later work.

## Testing

There are 114 pytest tests, each named after the spec requirement it checks.
- **Real file:** they check the full classification and every example in the spec.
- **Small made-up datasets** cover cases the real file doesn't have: ties, several drivers
  without a time, a deleted fastest lap, and malformed values.
- **Error handling:** bad files, bad driver codes, exit codes, and the prompt with scripted input.
- **Both run commands** are run as real subprocesses.
- **Design rules:** the code uses only the standard library, and modules import in the intended
  direction.

I also ran the suite on Python 3.10 to back up the minimum version.

Alongside the automated tests, I smoke-tested the tool by hand after each change. I ran it the
way a user would:
- drivers with different situations: RUS (pole), BOR (no Q3 time), VER (unclassified) and ALO
  (out in Q1)
- the interactive prompt with bad, unknown and empty input
- the plain `python -m qualifying` command on Python 3.10, without uv

I read the output each time. This also covers what the tests don't: they compare words rather
than exact spacing, so I checked the layout by eye. That's how I found the example rows in the
docs didn't match the real output's spacing.

## Future improvements

- **Teammate comparison by sector:** show where on the lap the driver gained or lost time
  against their teammate, not just the lap total.
- **More insights:** the remaining ones from the spec, plus `--json` output and warnings such as
  "BOR has no Q3 laps in the data".
- **A UI:** the CLI only displays results the core already computes, so a Streamlit or web front
  end could reuse the package unchanged.
- **Place unclassified drivers using practice data:** a driver with no valid qualifying lap
  (Verstappen here) could be placed using their FP3 lap times instead of being left
  unclassified. That matters most when several drivers have no time. It would need the FP3 file
  for the same event from the Tracing Insights repo.
- **More sessions:** support other sessions and events, with the grid size from configuration.
- **Weather:** re-join the weather data on session time.
- **Code quality tooling,** left out to fit the time box:
  - Ruff for linting and formatting, and mypy for type checks
  - a CI run on Python 3.10 and the latest version

  A trial run found 21 lint issues, mostly import order and naming and 6 type warnings about
  values that might be `None`. None of them are bugs today.

## Use of AI
I used Claude Code throughout. It drafted the analysis notebook, the spec, the tests,
the code and this write-up. I thoroughly reviewed the EDA and Spec before starting the
implementation. This has been reviewed but not at the line by line level. 

The Technical Task was not shown to the AI during this early phase as I didn't want to constrain the EDA and the art of the possible. But it was later used by me to validate the spec before proceeding with implementation as well as drafting the write-up.

I made the design decisions, and several changed its first suggestion:
- fixed cut-offs, so Bortoleto counts as a Q3 driver
- how drivers without a time are placed
- the teammate comparison instead of gap to pole
- an interactive prompt that never exits on bad input
- a dependency-free runtime
- the module structure, consolidating classes into models.py, separating out loading logic
- making it available as a package for incorporating into streamlit/web app later
- time formatting

I checked its work in three ways:
- every number in the spec was recomputed from the data
- the tests were seen failing before the code existed
- smoke-tests

That caught several mistakes, including a red-flag bug in the notebook and a wrong sign in a spec
example.
